## Hilo de la conversación

### 1. Retomar sesión anterior
- El usuario perdió la sesión anterior donde se discutía usar workers para multihilo
- Se había recomendado PM2 Cluster sobre worker_threads

### 2. Comparativa: PM2 Cluster vs worker_threads vs balanceador de carga
**Conclusión:** PM2 Cluster es la mejor opción porque:
- La carga es I/O-bound (PostgreSQL), no CPU-bound → worker_threads no aporta
- Cero cambios de código (solo config)
- PM2 maneja reinicio, graceful shutdown, reload sin downtime
- Balanceador externo (Nginx) es complementario, no sustituto

### 3. Creación de guía detallada
Se creó `CLUSTER_PM2_GUIDE.md` en la raíz con:

| Sección | Detalle |
|---|---|
| **Instancias recomendadas** | auth=3, analytics=2 (servidor 4 núcleos) |
| **Pools PostgreSQL** | Reducir default de `max: 50` a `max: 10` en `auth/src/db.js` y `analytics/src/db.js` |
| **WebSocket** | Sticky sessions vía `upstream` + `ip_hash` en Nginx porque `userConnections` es un Map en memoria |
| **pg_notify** | Se duplica entre workers (ineficiente pero no dañino) |
| **Prueba en Windows** | Usar `ecosystem.config.dev.js` con 2 instancias |
| **Despliegue en Debian** | Orden: respaldar → editar db.js → editar ecosystem → reload PM2 → actualizar Nginx |
| **Rollback** | Restaurar backup de ecosystem.config.js |
| **Monitorización** | Comandos para CPU, RAM, conexiones PG |
